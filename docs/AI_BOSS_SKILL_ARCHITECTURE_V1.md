# AI-BOSS Skill Architecture v1

## Persistent Skill Run

Основной скилл может работать дольше одного сообщения. Для пилота `business_diagnostic` ConversationService хранит в `thread.entryState` объект `activeSkillRun` и ограниченную историю `skillRunHistory`.

Жизненный цикл запуска:

- `active` — скилл начал работу;
- `waiting_for_user` — скиллу нужен один наблюдаемый сигнал;
- `completed` — критерий завершения выполнен, подготовлена передача следующему скиллу;
- `interrupted` — пользователь явно выбрал другую задачу.

Короткий ответ пользователя не запускает маршрутизацию заново: он продолжает активную диагностику с тем же `runId`. Объяснение термина или анализ документа допускаются как временный вспомогательный ход и не стирают запуск. Явный переход к инструменту, архитектуре, оценке зрелости или исполнению завершает текущий запуск как `interrupted`.

Запуск накапливает только рабочее состояние выбора следующего шага: сигналы, конкурирующие гипотезы, заданные вопросы, выбранное ограничение и подготовленную передачу. Он не подменяет `Observation`, `DiagnosticCase` и артефакты как источники подтверждённых данных.

Статус: целевая архитектура и карта постепенной миграции.  
Версия: 1.0.0.  
Назначение: превратить AI-BOSS из одного сложного pipeline в управляемую организацию специализированных способностей, сохранив живой разговор и работающий продукт.

## 1. Главный принцип

AI-BOSS — единая управляющая функция бизнеса, а не коллекция отдельных ботов.

Скиллы — это его специализированные способности. Они не должны конкурировать за пользователя или говорить разными голосами. Перед пользователем всегда один AI-BOSS, который сам собирает нужную внутреннюю команду под текущую ситуацию.

```text
сообщение или действие пользователя
→ понять намерение и состояние кейса
→ выбрать основной и вспомогательные скиллы
→ выполнить один полезный рабочий ход
→ проверить качество и полномочия
→ обновить память и артефакты
→ определить следующий скилл
```

Ключевое правило:

> Бизнес-скилл определяет, какой результат нужен. Коммуникационный скилл определяет, как получить его от пользователя. Оркестратор собирает команду. Память закрепляет результат. Контроль качества не позволяет выдать предположение за факт.

## 2. Результат аудита текущей системы

В текущем коде уже существуют почти все необходимые способности, но они оформлены неодинаково.

### Уже хорошо разделено

- классификация входа — `classify-input.js`;
- проверка целостности запроса — `intent-integrity-checker.js`;
- извлечение наблюдений — `observation-extractor.js`;
- причинный анализ — `graph-reasoner.js`;
- проверка эталонной модели — `reference-model-service.js`;
- достаточность данных — `data-sufficiency-checker.js`;
- режим работы — `ai-boss-mode-orchestrator.js`;
- ограничения ответа — `guardrails.js`;
- выбор гипотезы ограничения — `constraint-reasoner.js`;
- выбор следующего шага — `next-step-selector.js`;
- рекомендации инструментов — `tool-recommender.js`;
- сопровождение инструмента — `tool-workflow-service.js`;
- диагностика зрелости — `mini-app-diagnostics-service.js`, `maturity-calculator.js`;
- память — storage-слой, observations, snapshots и artifacts.

### Сейчас смешано

`ConversationService` одновременно:

- управляет входом;
- собирает аналитический контекст;
- вызывает модель;
- применяет guardrails;
- повышает thread до case;
- обновляет множество типов памяти;
- создаёт snapshots и artifacts;
- решает, показывать ли вход в кабинет.

`AIBossModeOrchestrator` уже выбирает состояние бизнеса, режим, горизонт и переход, но пока не выбирает формальные скиллы, не создаёт skill run и не проверяет критерий завершения выбранной способности.

`guardrails.js` одновременно содержит защитные правила, языковую политику и часть коммуникационного поведения. Это полезно для production, но затрудняет независимое тестирование коммуникационного качества.

### Главный архитектурный разрыв

Текущая система умеет выбирать **режим**, но ещё не управляет **командой скиллов**.

Режим отвечает на вопрос:

> Как AI-BOSS должен вести себя сейчас?

Скилл отвечает на вопрос:

> Какую законченную работу AI-BOSS выполняет сейчас и какой структурированный результат должен получить?

Оба слоя нужны одновременно.

## 4. Уровни ответственности

### 4.1. Skill Orchestrator

Оркестратор:

1. Понимает намерение пользователя.
2. Определяет состояние компании, кейса и разговора.
3. Получает shortlist допустимых скиллов из реестра.
4. Выбирает один основной скилл.
5. Выбирает до трёх вспомогательных скиллов.
6. Назначает коммуникационный скилл или режим.
7. Устанавливает результат текущего хода.
8. Запрещает преждевременные действия.
9. После выполнения проверяет критерий завершения.
10. Передаёт результат следующему скиллу.

Оркестратор не должен самостоятельно диагностировать бизнес или формировать готовый ответ.

### 4.2. Основной скилл

На один ход выбирается не более одного основного скилла. Он несёт ответственность за рабочий результат хода.

Примеры:

- `business_diagnostic` строит поле гипотез;
- `tool_facilitation` получает следующий ответ по инструменту;
- `document_analysis` создаёт snapshot документа;
- `next_step_selection` выбирает одно действие.

### 4.3. Вспомогательные скиллы

Они обеспечивают основную работу:

- `diagnostic_interview` формирует наблюдаемый вопрос;
- `observation_capture` сохраняет факты;
- `company_memory` обновляет контекст;
- `artifact_builder` создаёт результат;
- `progress_navigation` объясняет переход.

### 4.4. Всегда активные скиллы

На каждом содержательном ходе работают:

- `skill_orchestration`;
- `observation_capture`;
- `company_memory`;
- `confidence_control`;
- `communication_quality_control`.

Они могут не создавать видимый пользователю текст, но обязаны оставлять trace.

## 5. Контракт скилла

Контракты находятся в `src/domain/skill-registry.js`.

Обязательные поля:

```yaml
id: стабильный идентификатор
version: версия поведения
department: функциональное направление
kind: тип способности
activation: primary | supporting | always_on
purpose: законченный результат
whenToUse: условия запуска
whenNotToUse: ограничения
requiredContext: обязательный контекст
inputs: входы
outputs: структурированный результат
memoryUpdates: изменения памяти
artifactTypes: возможные артефакты
completionCriteria: критерии завершения
nextSkillCandidates: допустимые handoff
currentImplementation: текущие модули реализации
```

Контракт не задаёт готовые фразы. Он задаёт ответственность, границы и критерий результата.

## 6. Решение оркестратора

Целевая форма решения:

```json
{
  "intent": "понять причину слабых продаж",
  "conversationStage": "hypothesis_spread",
  "primarySkill": "business_diagnostic",
  "supportingSkills": [
    "diagnostic_interview",
    "observation_capture",
    "company_memory"
  ],
  "communicationSkill": "diagnostic_interview",
  "turnGoal": "отделить качество входящего потока от сбоя обработки",
  "requiredSignal": "наблюдаемый состав последних заявок",
  "prohibitedActions": [
    "объявлять нехватку людей причиной",
    "предлагать найм",
    "выбирать ограничение без верхней проверки"
  ],
  "completionCondition": "получен факт, который разделяет качество потока и пропускную способность",
  "nextSkillCandidates": [
    "constraint_prioritization",
    "diagnostic_interview"
  ]
}
```

## 7. Правила выбора скиллов

Shortlist строится детерминированно по четырём источникам:

1. Намерение и тип входа.
2. Состояние кейса и незакрытые вопросы.
3. Контекст экрана или активного инструмента.
4. Условия `whenToUse`, `whenNotToUse` и `requiredContext` из реестра.

Ранжирование:

```text
релевантность запросу
+ соответствие этапу
+ наличие обязательного контекста
+ ожидаемый информационный выигрыш
+ вклад в завершение кейса
- риск преждевременного вывода
- повтор уже выполненной работы
- конфликт с правами решений
```

LLM выбирает из shortlist и объясняет выбор. Она не получает право свободно вызывать любой скилл без ограничений реестра.

## 8. Коммуникационное состояние

Бизнес-кейс и состояние разговора должны храниться отдельно.

```json
{
  "userIntent": "",
  "currentStage": "",
  "communicationGoal": "",
  "knownFacts": [],
  "activeHypotheses": [],
  "missingSignal": "",
  "lastQuestion": "",
  "questionAnswered": false,
  "userConfusion": "",
  "repetitionRisk": [],
  "nextConversationMove": ""
}
```

Пользователь является источником фактов, наблюдений, примеров и документов. Он не обязан выбирать правильную гипотезу или знать причину проблемы.

## 9. Skill Run и handoff

Каждый запуск скилла должен иметь состояние:

```json
{
  "id": "skill_run_...",
  "skillId": "tool_facilitation",
  "skillVersion": "1.0.0",
  "status": "active",
  "turnGoal": "получить критерии целевого клиента",
  "inputRefs": [],
  "result": {},
  "factsAdded": [],
  "hypothesesAdded": [],
  "artifactsCreated": [],
  "missingInformation": [],
  "nextSkillCandidates": [],
  "startedAt": "",
  "completedAt": ""
}
```

Статусы:

- `planned`;
- `active`;
- `waiting_for_user`;
- `completed`;
- `superseded`;
- `failed`.

Handoff должен передавать не весь разговор, а структурированный результат работы.

## 10. Контрольные маршруты

### 10.1. Новый пользователь

```text
skill_orchestration
→ onboarding_conversation
→ intent_clarification
→ architecture_navigation или business_diagnostic
→ company_memory
```

### 10.2. Расплывчатый запрос

```text
intent_clarification
→ observation_capture
→ business_diagnostic
```

### 10.3. Конкретная бизнес-проблема

```text
business_diagnostic
+ diagnostic_interview
+ observation_capture
→ constraint_prioritization
→ next_step_selection
```

### 10.4. Последовательная сборка бизнеса

```text
architecture_navigation
→ tool_selection
→ tool_facilitation
→ artifact_builder
→ company_memory
→ progress_navigation
```

### 10.5. Пользователь просит инструмент

```text
intent_clarification при необходимости
→ tool_selection
→ concept_explanation
→ tool_facilitation
```

### 10.6. Заполнение инструмента в чате

```text
tool_facilitation
+ concept_explanation
+ observation_capture
→ artifact_builder
→ company_memory
```

### 10.7. Получен файл или ссылка

```text
document_analysis
→ observation_capture
→ company_memory
→ business_diagnostic или tool_facilitation
```

### 10.8. Пользователь открыл матрицу или гипотезу

```text
result_interpretation
→ diagnostic_interview или next_step_selection
```

```text

→ progress_navigation

```

### 10.10. Принят следующий шаг

```text
next_step_selection
→ execution_coordination
→ artifact_builder
→ progress_navigation
```

## 11. Как сохранить живость

Скилл не должен содержать полный шаблон ответа.

Он задаёт:

- цель;
- необходимые данные;
- допустимые действия;
- критерий завершения;
- структурированный результат.

Модель сохраняет свободу:

- выбирать естественную формулировку;
- учитывать стиль пользователя;
- сокращать ответ до двух фраз, когда этого достаточно;
- пояснять больше, когда пользователь не понимает;
- признавать неизвестное;
- пересобирать гипотезы при новых данных.

Антишаблонное правило:

> Одинаковым должен быть стандарт мышления и результата, а не текст ответа.

## 12. План миграции

### Этап 1. Реестр и аудит — выполнено в v1

- создан машинно-читаемый реестр;
- зафиксированы владельцы ответственности;
- текущие модули сопоставлены со скиллами;
- добавлена проверка контрактов;
- production-поведение не изменено.

### Этап 2. Оркестратор выбора — выполнено в shadow mode

- добавлен deterministic shortlist;
- добавлен `SkillSelectionDecision`;
- выбранные скиллы сохраняются в `decisionObject.skillSelection`;
- выбор работает в shadow mode и не меняет пользовательский ответ;
- отдельный eval-набор проверяет маршрутизацию на 35 контрольных ситуациях.

### Этап 3. Первый пилотный маршрут — выполнено

Перенести только маршрут:

```text
business_diagnostic
→ diagnostic_interview
→ observation_capture
→ company_memory
→ next_step_selection
```

Реализовано:

- предварительный выбор скилла выполняется до reasoner;
- только `business_diagnostic` получает исполняемый контракт;
- контракт держит конкурирующие гипотезы из разных слоёв;
- при слабом сигнале допускается только один вопрос о наблюдаемом факте;
- выбор ограничения и `actionWave` блокируются до прохождения evidence gate;
- количественный или подтверждённый сигнал сохраняет переход к решению;
- текущий reasoner и эвристика остаются fallback;
- флаг `SKILL_ORCHESTRATOR_DIAGNOSTIC_ENABLED=false` мгновенно отключает пилот;
- отдельная проверка запускается командой `npm run skills:pilot:check`.

Результат внутреннего production-like пилота:

- добавлено 20 многоходовых сценариев по продажам, финансам, собственнику, стратегии, исполнению, удержанию, инструментам, URL и слабому входу;
- проверяются не только route и action, но и многослойность поля гипотез, один наблюдаемый вопрос, отсутствие преждевременного ограничения и допустимый причинный слой вывода;
- запрос конкретного инструмента имеет приоритет над общим словом предметной области;
- сильным считается связанный бизнес-факт, а не любое число в сообщении;
- черновые гипотезы больше не меняют режим бизнеса до подтверждения;
- результат: `20/20` командой `npm run skills:pilot:eval`;
- полный старый регресс сохранён.

### Этап 4. Skill Run

- добавить состояние запуска;
- поддержать `waiting_for_user`;
- продолжать незавершённый скилл после паузы;
- сохранять handoff.

### Этап 5. Инструменты и платформа

- подключить `architecture_navigation`;
- перевести tool workflow на общий контракт;
- передавать контекст экрана в `platform_support`;
- связывать завершение инструмента с архитектурой.

### Этап 6. Полная декомпозиция ConversationService

Оставить в нём только транспортную оркестрацию:

```text
load context
→ run skill orchestrator
→ execute selected skills
→ persist result
→ return response
```

## 13. Что пока не делать

- не создавать отдельного агента на каждый скилл;
- не делать multi-agent zoo;
- не переносить все промпты сразу;
- не давать LLM свободно выбирать любой скилл;
- не создавать скилл на каждый пользовательский вопрос;
- не удалять текущие guardrails до прохождения регрессий;
- не менять production pipeline до shadow-проверки.

## 14. Критерий успешности архитектуры

Архитектура работает, если:

- на каждом ходе понятно, какой скилл отвечает за результат;
- основной скилл один;
- вспомогательные способности не дублируют его;
- пользователь не замечает внутренних переключений;
- ответы остаются живыми;
- память обновляется структурированно;
- незавершённая работа продолжается после паузы;
- каждый сильный кейс заканчивается артефактом или подтверждённым следующим шагом;
- качество каждого скилла можно проверить отдельно.

## 15. Следующий технический шаг

Перейти к устойчивому `Skill Run` только для проверенного маршрута `business_diagnostic`:

1. Создавать идентификатор запуска и сохранять его состояние `waiting_for_user`.
2. На следующем сообщении продолжать тот же запуск, а не выбирать маршрут заново без причины.
3. Сохранять подтверждённый сигнал, выполненный критерий и handoff в следующий скилл.
4. Добавить прерывание и смену маршрута, если пользователь явно изменил задачу.
5. Сначала проверить продолжение на многоходовых сценариях, затем подключать следующий исполняемый скилл.

Остальные маршруты остаются в shadow mode до отдельной проверки.
