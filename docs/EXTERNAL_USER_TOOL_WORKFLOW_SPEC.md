# AI-BOSS External User Tool Workflow Spec

Дата: 16.05.2026

Статус на 14.08.2026: целевая карта tool workflow. Упоминания Mini App описывают прежний интерфейсный вариант; ближайшая реализация должна вести `tool_selection` и `tool_facilitation` в Telegram, используя `/app` как дополнительную веб-платформу.

## 1. Зачем нужен этот слой

AI-BOSS должен работать с внешними пользователями как самостоятельная управляющая функция бизнеса, а не только как чат или диагностический экран.

Пользователь должен уметь:

- зарегистрироваться и получить личный кабинет;
- видеть свою компанию, текущий маршрут и накопленную информацию;
- идти по архитектуре бизнеса слой за слоем;
- заполнять инструменты в правильной последовательности;
- получать подсказки по каждому инструменту;
- хранить результаты так, чтобы AI-BOSS всегда видел актуальный контекст;
- возвращаться к документам, обновлять их и продолжать работу без потери смысла.

Главная продуктовая идея:

> AI-BOSS не просто отвечает на вопросы. Он ведёт пользователя по программе управленческих инструментов, собирает память компании и помогает превращать ответы в рабочие артефакты.

## 2. Основной сценарий

Текущий реальный сценарий:

1. Группа идёт последовательно по архитектуре бизнеса.
2. Начинает с контура собственника.
3. Берёт один инструмент за другим.
4. Заполняет инструмент.
5. В результате у пользователя копится информация о компании.
6. AI-BOSS должен хранить эту информацию и использовать её в каждом следующем ответе.

Целевой маршрут:

```text
Пользователь регистрируется
  -> попадает в личный кабинет
  -> видит текущий слой архитектуры
  -> получает следующий инструмент
  -> выбирает способ заполнения
  -> заполняет через Google-документ или чат
  -> AI-BOSS сохраняет результат
  -> создаёт snapshot и observations
  -> обновляет память компании
  -> предлагает следующий инструмент
```

## 3. Два способа заполнения инструмента

### 3.1. Google document mode

AI-BOSS даёт пользователю личную копию шаблона.

Поток:

1. В каталоге есть мастер-шаблон инструмента.
2. AI-BOSS создаёт копию шаблона для конкретного пользователя, компании и кейса.
3. Пользователь получает ссылку на свою копию.
4. Пользователь заполняет документ.
5. AI-BOSS сохраняет ссылку и статус документа.
6. Пользователь нажимает “Проанализировать” или пишет боту, что документ обновлён.
7. AI-BOSS читает документ, делает короткий структурированный вывод и сохраняет snapshot.
8. Полезные выводы превращаются в observations и попадают в память компании.

Правила:

- мастер-шаблон никогда не изменяется;
- у каждого пользователя своя копия;
- одна компания может иметь несколько копий одного инструмента по разным кейсам или версиям;
- ссылка на документ не равна памяти, памятью является snapshot и извлечённые observations;
- если документ изменился, AI-BOSS должен уметь перечитать его по кнопке или команде.

### 3.2. Chat guided mode

AI-BOSS задаёт вопросы из шаблона прямо в чате и сам заполняет структуру инструмента.

Поток:

1. Пользователь выбирает инструмент.
2. AI-BOSS объясняет, зачем он нужен и какой результат получится.
3. AI-BOSS задаёт вопросы из шаблона не как анкету, а как живое сопровождение.
4. Ответы пользователя сохраняются как tool answers.
5. AI-BOSS может уточнять противоречия и подсказывать, как лучше сформулировать.
6. После заполнения AI-BOSS создаёт или обновляет личный Google-документ пользователя.
7. Результат сохраняется как snapshot, observations и artifact.

Правила:

- бот не должен заставлять пользователя заново писать то, что уже известно из компании, документов или прошлых инструментов;
- если часть данных уже есть, бот предлагает предзаполнение и просит подтвердить;
- если пользователь отвечает голосом, текст транскрипта должен попадать в ту же структуру ответов;
- если пользователь не знает ответ, бот должен помогать понять, какие данные нужны, а не давить на него выбором.

## 4. Что должен знать AI-BOSS об инструменте

Каждый инструмент в каталоге должен быть не просто ссылкой.

Текущий источник каталога для MVP:

- Google Sheet: `1ub9feLgp31fSygIA7qcfjGJeiwSJZXEQKWc_jbKIj7U`;
- лист `gid=675359757`;
- синхронизация в Supabase: `npm run tools:sync`;
- dry-run без записи: `npm run tools:sync:dry`;
- рантайм Mini App сначала читает `public.tools`, а если каталог недоступен или пустой, использует встроенный fallback.

Важное ограничение:

- CSV-экспорт Google Sheets отдаёт текст ячейки, но не всегда отдаёт URL, скрытый внутри гиперссылки;
- если ссылка оформлена как hyperlink с красивым текстом, AI-BOSS сохранит `link_label`, но не сможет сам достать настоящий URL без Google Sheets API/Google OAuth/Apps Script;
- для MVP лучше хранить прямой URL в отдельной колонке или прямо в ячейке “Ссылка на инструмент”.

Минимальная структура `ToolTemplate`:

- `id`;
- `slug`;
- `title`;
- `layer_key`;
- `domain_key`;
- `purpose`;
- `when_to_use`;
- `expected_result`;
- `template_google_file_id`;
- `template_url`;
- `questions`;
- `fields`;
- `examples`;
- `completion_rules`;
- `analysis_rules`;
- `observations_mapping`;
- `next_tool_logic`;
- `version`;
- `is_active`.

AI-BOSS должен понимать по каждому инструменту:

- зачем он нужен;
- на каком слое архитектуры работает;
- какой разрыв помогает увидеть;
- какие ответы считаются достаточными;
- какие признаки говорят, что инструмент заполнен слабо;
- какие выводы можно делать из результата;
- какие выводы делать нельзя;
- какой следующий инструмент логично предложить.

## 5. Память компании

У пользователя должна копиться не просто история сообщений, а рабочая память компании.

Источники памяти:

- ответы в чате;
- заполненные инструменты;
- Google-документы;
- snapshots по документам;
- observations из диагностики;
- решения пользователя;
- артефакты;
- текущий маршрут по слоям.

Перед каждым ответом AI-BOSS должен поднимать актуальный контекст:

- профиль компании;
- активный кейс;
- текущий слой и инструмент;
- какие инструменты уже заполнены;
- какие документы есть;
- какие snapshots актуальны;
- какие observations подтверждены;
- какие гипотезы и next steps уже есть;
- какие открытые вопросы остались.

Правило:

> AI-BOSS не должен отвечать как будто видит пользователя впервые, если в системе уже есть его компания, документы и заполненные инструменты.

## 6. Новые сущности

### 6.1. `ToolTemplate`

Каталог мастер-инструментов.

Хранит описание инструмента, привязку к архитектуре, шаблон Google-документа и правила работы.

### 6.2. `ToolInstance`

Личный экземпляр инструмента у конкретной компании или кейса.

Поля:

- `workspace_id`;
- `company_id`;
- `case_id`;
- `tool_template_id`;
- `status`;
- `current_step`;
- `progress_percent`;
- `created_by_app_user_id`;
- `started_at`;
- `completed_at`;
- `version`.

Статусы:

- `not_started`;
- `in_progress`;
- `waiting_for_user`;
- `submitted`;
- `analyzed`;
- `needs_update`;
- `completed`;
- `archived`.

### 6.3. `ToolDocumentInstance`

Личная копия Google-документа по инструменту.

Поля:

- `tool_instance_id`;
- `template_google_file_id`;
- `google_file_id`;
- `google_file_url`;
- `google_folder_id`;
- `copy_status`;
- `access_status`;
- `last_read_at`;
- `last_snapshot_id`;
- `version`.

Статусы копирования:

- `pending`;
- `created`;
- `failed`;
- `manual_link_added`.

### 6.4. `ToolAnswer`

Ответ пользователя на конкретный вопрос или поле инструмента.

Поля:

- `tool_instance_id`;
- `question_key`;
- `answer_text`;
- `source`;
- `confidence`;
- `status`;
- `evidence_message_id`;

Источники:

- `chat_text`;
- `chat_voice`;
- `mini_app_form`;
- `google_document`;
- `ai_prefill`;
- `manual_admin`.

Статусы:

- `suggested`;
- `confirmed`;
- `corrected`;
- `rejected`;
- `superseded`.

### 6.5. `ToolSnapshot`

Структурированный вывод по заполненному инструменту.

Поля:

- `tool_instance_id`;
- `summary`;
- `key_findings`;
- `risks`;
- `open_questions`;
- `extracted_observations`;
- `recommended_next_tool`;
- `created_at`;
- `version`.

### 6.6. `ToolJourney`

Маршрут пользователя по программе инструментов.

Поля:

- `workspace_id`;
- `company_id`;
- `case_id`;
- `current_layer_key`;
- `current_tool_instance_id`;
- `completed_tool_template_ids`;
- `next_tool_template_ids`;
- `status`;
- `progress_summary`.

## 7. Личный кабинет пользователя

Кабинет должен показывать не только диагностику, но и путь работы.

Главные блоки:

- профиль компании;
- текущий слой архитектуры;
- текущий инструмент;
- прогресс по программе;
- документы пользователя;
- заполненные инструменты;
- последние выводы AI-BOSS;
- следующий рекомендуемый инструмент;
- кнопка “Спросить AI-BOSS”.

Минимальные экраны:

- регистрация / заявка на доступ;
- главная;
- программа по 11 слоям;
- текущий инструмент;
- мои документы;
- память компании;
- история инструментов;
- AI-BOSS overlay.

## 8. Web Architecture Builder

Помимо личного кабинета нужен отдельный рабочий интерфейс, где пользователь строит архитектуру своего бизнеса по шагам.

Это не должна быть статичная схема 11 слоёв. Это должен быть guided-builder:

```text
слой архитектуры
  -> смысл слоя
  -> текущие вопросы
  -> подходящий инструмент
  -> способ заполнения
  -> сохранённый результат
  -> вывод AI-BOSS
  -> следующий шаг
```

Главная задача интерфейса:

> Пользователь видит не “кучу разделов”, а понятный путь: где он сейчас, зачем этот шаг, что уже собрано и что нужно сделать следующим.

### 8.1. Что пользователь должен видеть

На экране конструктора:

- 11 слоёв архитектуры;
- текущий активный слой;
- статус каждого слоя;
- какие инструменты уже заполнены;
- какие инструменты рекомендованы дальше;
- какие документы связаны со слоем;
- какие выводы AI-BOSS уже сделал;
- какие вопросы ещё открыты;
- какой следующий шаг сейчас самый полезный.

Статусы слоя:

- `not_started` - ещё не начинали;
- `in_progress` - слой в работе;
- `has_draft` - есть черновые ответы или документ;
- `needs_review` - нужно проверить или подтвердить вывод;
- `completed` - слой собран на текущем уровне;
- `needs_update` - данные устарели или появился новый сигнал.

### 8.2. Карточка слоя

Каждый слой должен открываться в карточку.

Карточка слоя показывает:

- что означает слой простым языком;
- почему он важен для бизнеса;
- какие инструменты относятся к слою;
- что уже заполнено;
- что AI-BOSS считает известным;
- что пока является гипотезой;
- какие документы прикреплены;
- какую часть архитектуры нужно заполнить следующей.

Пример для `owner_context`:

```text
Контур собственника

Здесь мы фиксируем, чего хочет собственник, куда ведёт бизнес, какую роль занимает и какие решения готов принимать.

Заполнено:
- текущая цель собственника;
- горизонт;
- роль в бизнесе.

Открыто:
- критерии успеха;
- ограничения по времени и энергии;
- что собственник хочет делегировать.

Следующий инструмент:
Карта целей и роли собственника.
```

### 8.3. Guided-step вместо анкеты

Конструктор не должен давать пользователю весь список полей сразу.

Правильная логика:

1. AI-BOSS показывает смысл текущего шага.
2. Показывает, что уже известно.
3. Предлагает один понятный следующий блок.
4. Даёт выбор: заполнить в документе или пройти через чат.
5. После заполнения показывает короткий вывод.
6. Обновляет слой и предлагает следующий шаг.

Это сохраняет ощущение живого сопровождения, а не формы.

### 8.4. Архитектура как накопительная карта

Веб-интерфейс должен показывать, что архитектура постепенно собирается.

Минимальные визуальные блоки:

- карта 11 слоёв;
- прогресс по слоям;
- текущий фокус;
- заполненные инструменты;
- открытые пробелы;
- последние выводы;
- следующий рекомендуемый инструмент.

Пользователь должен в любой момент понимать:

- “что мы уже собрали”;
- “что ещё не ясно”;
- “где сейчас главный фокус”;
- “какой документ или инструмент нужно заполнить дальше”.

### 8.5. Роль AI-BOSS в builder

В builder AI-BOSS действует как проводник.

Он должен:

- объяснять текущий шаг;
- помогать выбрать инструмент;
- отвечать на вопросы по текущему экрану;
- подсказывать, как заполнить поле;
- проверять заполненный документ;
- подсвечивать противоречия;
- связывать новый ответ с уже накопленным контекстом;
- предлагать следующий слой или инструмент.

AI-BOSS не должен:

- заставлять пользователя самому разбираться в структуре;
- показывать 11 слоёв как пустую таблицу;
- давать длинный список всех инструментов без маршрута;
- просить повторно вводить то, что уже есть в документах или чате.

### 8.6. Минимальные экраны builder

Post-MVP web routes:

```text
/mini-app/architecture
/mini-app/architecture/:layerKey
/mini-app/architecture/:layerKey/tools
/mini-app/architecture/:layerKey/tools/:toolInstanceId
/mini-app/architecture/:layerKey/documents
/mini-app/architecture/:layerKey/summary
```

Каждый экран должен иметь:

- назад;
- на главный экран;
- “Спросить AI-BOSS”;
- текущий контекст слоя;
- понятный следующий шаг.

## 9. Работа с внешними пользователями

Внешний пользователь не должен автоматически получать полный доступ.

Минимальная модель доступа:

1. Пользователь запускает бота.
2. Бот создаёт access request или pending user.
3. Администратор подтверждает доступ.
4. Пользователь получает кабинет.
5. Создаётся workspace, company, membership и активный case.

Требования:

- пользователь видит только свои компании и документы;
- пользователь не может открыть документы другого пользователя;
- документы создаются как отдельные копии;
- системные шаблоны защищены от изменения;
- все действия пишутся в audit / analytics events.

## 10. Google Drive модель

### 10.1. MVP-вариант

Для первого рабочего запуска достаточно service account и app-owned папки.

Структура Drive:

```text
AI-BOSS Companies
  /<company_id> - <company_name>
    /tools
      /<tool_slug>
        /v1 - <tool title> - <date>
```

AI-BOSS:

- копирует мастер-шаблон в папку компании;
- сохраняет `google_file_id` и ссылку;
- выдаёт пользователю ссылку;
- читает документ по сервисному доступу;
- делает snapshot по кнопке.

### 10.2. Post-MVP

Позже можно добавить:

- Google OAuth;
- Google Picker;
- пользовательские Drive-папки;
- автоматическую проверку изменений;
- версионное сравнение документа;
- запись ответов в Google Docs / Sheets по структурным полям.

## 11. Как AI-BOSS сопровождает пользователя

AI-BOSS должен вести себя как проводник по инструменту.

Он должен:

- объяснять, зачем этот инструмент сейчас;
- показывать, какой результат получится;
- помогать выбрать между заполнением в документе и в чате;
- задавать вопросы из шаблона естественно;
- использовать уже известные данные;
- предупреждать, если ответ слишком общий;
- подсвечивать противоречия;
- объяснять термины простым языком;
- сохранять результат;
- предлагать следующий шаг.

Он не должен:

- просто отправлять ссылку и исчезать;
- заставлять проходить длинную анкету;
- давать общий совет вместо заполнения инструмента;
- менять мастер-шаблон;
- делать выводы из документа, если доступа или данных недостаточно;
- утверждать то, что пользователь не подтвердил.

### Phase 9.4. Personal Google copy service

Сервис:

- получает `tool_template_id`;
- создаёт копию Google-шаблона;
- кладёт копию в папку компании;
- сохраняет `ToolDocumentInstance`;
- возвращает ссылку пользователю.

### Phase 9.5. Guided chat filling

AI-BOSS:

- запускает `ToolFillSession`;
- задаёт вопросы из инструмента;
- сохраняет ответы;
- даёт подсказки;
- заполняет структуру инструмента;
- готовит документ к обновлению.

### Phase 9.6. Write-back to document

AI-BOSS:

- переносит структурированные ответы в личный Google-документ;
- обновляет snapshot;
- создаёт observations;
- предлагает следующий инструмент.

## 13. Acceptance criteria

Считаем слой готовым, если:

- внешний пользователь может запросить доступ и получить кабинет;
- у пользователя есть личная компания и активный кейс;
- пользователь может открыть web-builder архитектуры;
- пользователь видит 11 слоёв и статус каждого слоя;
- пользователь видит текущий слой, инструмент, документы и следующий шаг;
- пользователь видит текущий слой и текущий инструмент;
- AI-BOSS может выдать личную копию Google-шаблона;
- копия создаётся для конкретного пользователя, а мастер-шаблон не меняется;
- пользователь может заполнить инструмент в Google-документе;
- пользователь может заполнить инструмент через чат;
- ответы сохраняются как `ToolAnswer`;
- заполненный документ сохраняется как `ToolDocumentInstance`;
- AI-BOSS может проанализировать документ и сохранить `ToolSnapshot`;
- полезные выводы становятся observations;
- AI-BOSS использует заполненные инструменты как контекст в следующих ответах;
- пользователь не видит чужие инструменты и документы;
- администратор может видеть прогресс внешних пользователей.

## 14. Главный риск

Главный риск - сделать много хранения, но не сделать сопровождение.

Поэтому приоритет такой:

1. Сначала маршрут инструмента.
2. Потом личный документ.
3. Потом сохранение ответов.
4. Потом snapshot.
5. Потом контекст в ответах бота.
6. Только потом автосинхронизация и сложная Google-интеграция.

Короткая формула:

> AI-BOSS должен не просто хранить документы, а вести пользователя от инструмента к инструменту и каждый раз становиться умнее за счёт уже заполненного контекста.
